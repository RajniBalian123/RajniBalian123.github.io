Deep dive — featured project

How the metrics aggregator earns trust

LinkedIn lists jobs. This site shows thinking. This is the write-up format used for every project: problem → approach → what proves it works.

The problem

Leadership asks one question — “how are we doing?” — and gets three different numbers from three business units, none with a source attached. The fix isn’t a prettier dashboard. It’s provenance.

The approach

Each BU publishes metrics through the same contract. An aggregation layer joins them, attaches lineage, enforces who can see what, and scores trust from freshness + quarantine rate + owner sign-off. If trust is low, the number is shown — with the reason it’s low, right next to it.

1 · IngestBU metrics + schema check
2 · QuarantineBad rows flagged, not dropped
3 · AggregateJoin + lineage attached
4 · Score trustFreshness · completeness · owner
5 · ServeAPI + dashboard, RBAC enforced

How I work

Four rules I ship by

This section is what LinkedIn can’t show — and what hiring managers actually probe in interviews.

1. Evals first

No feature ships without a golden set. I build the test before the prompt, so “it feels better” becomes a number.

2. Groundedness gates

Every answer must cite its source or abstain. Ungrounded answers don’t reach the user — they go to a review queue.

3. Abstain & escalate

Low confidence isn’t a failure mode to hide. It’s a routing decision: cached answer, cheaper model, or a human.

4. Cost is a feature

Tokens, compute, and latency are tagged per plant / per BU / per user from day one — not retrofitted after the bill arrives.
